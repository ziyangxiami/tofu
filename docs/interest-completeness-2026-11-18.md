# 影视标记缺失与完成计数修复

问题来源：[doufen-org/tofu#122 的评论](https://github.com/doufen-org/tofu/issues/122#issuecomment-6817732358)。反馈账号公开显示 7,085 条“看过”，Excel 只有 1,101 条；0.13.4 诊断记录仍将整个书影音任务记为 `completed`、`count=total=8567`。

## 排查证据

2026-11-18 对该账号的公开数据做了有限、未登录的只读检查，没有读取反馈者的浏览器、数据库或登录凭据。

- [公开电影列表](https://movie.douban.com/people/film101/collect)仍显示 7,085 条，网页为每页 15 条、共 473 页；末页实际返回第 7,081～7,085 条，共 5 条。
- 同一数字账号、`movie/done`、`start=3500&count=50` 的接口请求，带 `for_mobile=1` 时返回 25 条，去掉该参数返回 49 条；两者均报告 `total=7085`、`count=50`。其他边界请求同样出现实际数组短于接口容量的情况。
- 对照从第 3,495 条开始的公开网页，能读到批量移动接口遗漏的标记；其中一个遗漏标记在单条接口请求中也可读取。接口短数组不能直接解释为内容已删除。
- 旧抓取逻辑固定按请求容量 50 前进，不核对实际唯一记录数；`Task.complete()` 又把实际进度直接覆盖为接口总数。因此日志不能证明备份完整。Excel 导出遍历整个分类索引，没有 1,101 条的上限。

这些证据确认接口漏项和完成计数失真，不能独立还原反馈者当时恰好剩余 1,101 条的每一个响应。本次以同规模模拟响应回归该具体数量组合，并单独验证真实公开页面的解析。

## 修复行为

- 书影音请求去掉强制移动端过滤参数；服务端下调分页 `count` 时，按实际返回的分页容量前进，不再固定跳过 50 条。
- 每个类型、状态单独核对总数和成功保存的唯一 ID。重复页不累计进度；主键与条目冲突、错误状态、错误偏移量、无效容量和扫描中变化的总数明确失败。
- 影视标记数量不足时，扫描对应“想看／在看／看过”的公开网页，补齐尚未读取的标记；保留已经从接口取得的评分等较丰富字段。网页中无法取得的豆瓣总体评分不虚构，显示未提供。
- 网页逐页核对数量、范围、页码、总页数及重复条目。失败时不发布暂存数据，也不替换旧快照。其他书影音分类数量不足同样明确失败。
- 完成数量来自真实保存的唯一记录，发布前须与逐分类核验后的总数一致。新增分类计数、补齐触发和核验结果诊断，不记录账号、URL、Cookie 或条目内容。

网页补齐会增加只读请求，仍通过既有服务执行并遵守全局请求间隔；公开网页受限或内容在备份过程中变化时，需要重试。

## 验证范围

离线回归使用真实 Dexie、fake-indexeddb、扩展 HTML 解析器及随扩展附带的 SheetJS：模拟接口标称 7,085 条但只有 1,101 个唯一标记，补齐后原子发布 7,085 条，并实际写出、读回含 7,085 条数据及一行表头的 XLSX。另覆盖分页降容、短数组、重复页、受限网页、总数变化、ID 冲突、零数据和诊断隐私。

`node extension/tests/run.mjs` 的全部 12 套离线回归通过，包括新增的 16 个完整性场景。三个改动或新增的 JavaScript 文件语法检查及 `git diff --check` 通过。

真实公开页面验证仅限已读取的页面及接口样本；未执行反馈者登录环境下的完整 7,085 条备份，没有发布扩展商店版本。
