# 0.13.4 后续修复与验收记录

日期：2026-11-06。本文更新首轮 0.13.3 遗留问题的状态。

## 已补修

### 每类任务的快照原子发布

所有常规备份任务先写持久化暂存数据库。网络请求不在 IndexedDB 事务内执行；任务完成后，通过主账号库的一个短事务发布所属表、版本和提交回执。相册与照片、豆列与条目、豆邮与联系人分别一起提交。不同类别可独立成功，整份 Job 并非跨所有类别的全局事务。

分页失败、后台中断或提交失败时，该类别已发布的旧数据保持不变。发布成功但会话尚未记录完成时，恢复通过数据库回执识别成功，避免再次抓取/发布。暂存初始化与完成标志原子写入；重新初始化时必须使旧分页断点失效。成功发布后清理对应孤儿暂存，删除账号时同时清理其暂存数据。图片文件缓存继续采用逐项保存，并在主要任务后运行。

验证使用仓库真实 Dexie 与 fake-indexeddb 的完整事务实现，包含中途失败、重启恢复、父子表回滚、初始化失败、并发类别、增量游标和实际 Job 集成；它不是 Chrome 原生 IndexedDB 的实机验收。

连续两次后台退出的断点重置窗口已补测试：持久化重置标记必须等到会话中的旧断点清除并保存成功后才确认。备份卡片更新时间也改为真实发布时刻，失败保留旧时间，首次未成功显示“尚未完成备份”；迁移不生成虚假的目标账号备份卡片。

### 迁移链路

注册关注、黑名单、书影音标记、日记、评论、读书笔记六类任务。执行前展示来源账号、目标账号、已发布版本和条数，由用户确认。执行时再次检查绑定；迁移类别串行执行，任何失败停止后续类别。

每条写请求发出前持久保存 pending；只有明确成功回执才记为 confirmed。独立本地 journal 在后台清空 Job 后仍保留，因此重新创建同一来源/目标/类型/版本的迁移也不会重发未知结果。HTTP/解析失败、矛盾结果均不能算成功。富文本使用真实 Worker HTML parser 验证，避免空正文或丢失格式。

同一来源、目标和类型的旧版本若有 pending，也会阻止新版本迁移，不能通过新做一次备份绕过未知结果；已确认的成功记录继续按版本处理。

遇到“结果尚未确认”时，应在目标账号核对相关内容；本版没有提供清空回执或自动强制重发按钮。若结果仍不明，应保留 journal 并停止该批迁移。测试全部使用模拟目标接口，本次没有向真实豆瓣账号发布内容、上传迁移图片、关注或拉黑。

### Windows 启动器与设置

启动器改用明确的 Unicode API，从 exe 所在目录读取 `[extension] id` 并定位 Chromium 和 userdata；校验扩展 ID，使用可写且正确引用的命令行，清理进程/注册表句柄。CMake 改为 GUI 入口、RC 图标、正确依赖库与构建输出目录。

宿主 clang 编译并运行真实 main.c 配合 Win32 API mock 的回归已通过；本机无 Windows 工具链，未生成或运行 Windows exe。旧启动器仍使用历史更新站点，不会自动安装本仓库的扩展。具体构建方式见 chrome/README.txt。

Settings.apply 的嵌套目标复用也已修复，混合嵌套/顶层配置测试通过。
